# معمارية الروابط الثابتة `/t/<code>`

آخر تحديث: 2026-09-27 (sys-architect). تصف الموجود في `systems/shortlinks/` كما بناه sys-builder.

## 1. الفكرة
الشريحة والباركود يحملان رابطاً ثابتاً لا يتغير أبداً: `https://<domain>/t/<code>`. الوجهة (منيو، تقييم قوقل، ...) تتغير في السجل فقط، ونعيد البناء والرفع. لا نعيد برمجة شريحة.

## 2. المكونات (موجودة)
| الملف | الدور |
|---|---|
| `shortlinks/config.json` | الدومين في سطر واحد (`https://example.com` مؤقتاً). تغيير الدومين = تعديل هذا السطر ثم البناء. |
| `shortlinks/links.json` | سجل الروابط: `code, client, place, dest, status (active/cancelled), programmed`. |
| `shortlinks/build.js` | Node بدون مكتبات. يتحقق: الكود `^[a-z0-9]{3,16}$` وغير محجوز، لا تكرار، place إلزامي، الوجهة https سليمة (`new URL`، بلا مسافات أو `<>"'`) ولا ترجع لـ `/t/` على دوميننا، لا حذف لكود منشور (`published.txt`)، و`_redirects` ≤ 2000 سطر. يولد `dist/`. |
| `dist/t/<code>/index.html` | meta refresh 0 + `location.replace` + رابط يدوي، noindex. يشتغل على أي استضافة ثابتة. |
| `dist/_redirects` | تحويل 302 لكل كود (بشرطة وبدونها). سطر `/* /404.html 404` انحذف (جولة 2). |
| `dist/t/inactive/index.html` | صفحة بديلة للروابط الملغاة. |
| `dist/404.html` | رسالة + JS يحول `/t/ABC` أو `/t/abc` إلى `/t/abc/`. |
| `dist/links.txt` | الروابط الكاملة للبرمجة في الشرائح. |

## 3. طريقتان للتحويل (طبقتان)
1. `_redirects` (302 من الخادم، أسرع) على Netlify وCloudflare Pages.
2. صفحات HTML (meta refresh + JS) احتياط، وهي الطريقة الوحيدة على GitHub Pages (لا يقرأ `_redirects`؛ لا يوجد ذكر له في توثيق GitHub Pages = غير مؤكد رسمياً لكنه ليس ميزة موثقة).
302 وليس 301 عمداً: المتصفح لا يحفظ 302 فتغيير الوجهة يسري فوراً.

**تنبيه Netlify (shadowing):** لأن الملف `t/<code>/index.html` موجود، قاعدة 302 بدون `!` لا تنفذ لذاك المسار ويُخدم ملف HTML بدلها (التحويل يبقى يشتغل لكن عبر meta refresh). لو نبي 302 من الخادم على Netlify نضيف `!` (force). على Cloudflare Pages التوثيق يقول: «Redirects are always followed, regardless of whether or not an asset matches».

**الرابط المعتمد للبرمجة:** `https://<domain>/t/<code>/` بحروف صغيرة ومع الشرطة الأخيرة (كما في `links.txt`).

## 4. نتائج التوثيق (مصادر رسمية)
| السؤال | Netlify | Cloudflare Pages | GitHub Pages |
|---|---|---|---|
| هل مسارات `_redirects` تفرق بين الحروف؟ | نعم: «Paths are case-sensitive» ([المصدر](https://docs.netlify.com/manage/routing/redirects/overview/)) | غير مؤكد (التوثيق لا يذكرها) ([المصدر](https://developers.cloudflare.com/pages/configuration/redirects/)) | لا ينطبق |
| `/* /404.html 404` | مدعوم؛ ويكفي وجود `404.html` بدون قاعدة ([المصدر](https://docs.netlify.com/manage/routing/redirects/redirect-options/)) | **غير مدعوم**: `_redirects` يقبل 301/302/303/307/308، و200 (rewrite) للمسارات الداخلية، ولا يقبل 404 ([المصدر](https://developers.cloudflare.com/pages/configuration/redirects/)). لكن `404.html` في الجذر يُخدم تلقائياً لأي ملف غير موجود ([المصدر](https://developers.cloudflare.com/pages/configuration/serving-pages/)) | `404.html` في المصدر يُعرض للصفحات غير الموجودة ([المصدر](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-custom-404-page-for-your-github-pages-site)) |
| حد عدد التحويلات | غير مؤكد | 2,000 ثابت + 100 ديناميكي ([المصدر](https://developers.cloudflare.com/pages/configuration/redirects/)) = نحو **1,000 كود** لأن كل كود سطرين (بشرطة وبدونها). بعدها Bulk Redirects أو الاعتماد على صفحات HTML | لا ينطبق |

**النتيجة للتصميم:** الحروف الكبيرة (`/t/ABC`) لا تطابق قواعد Netlify فتسقط إلى `404.html` اللي يصححها بـ JS. سطر `/* /404.html 404` انحذف لأن الاستضافتين تخدمان `404.html` تلقائياً.

## 5. حدود الخطط المجانية
| | GitHub Pages | Cloudflare Pages (Free) | Netlify (Free) |

| الحجم/الملفات | الموقع ≤ 1 GB | ≤ 20,000 ملف، الملف ≤ 25 MiB | غير مؤكد |
| النطاق الترددي | حد مرن 100 GB/شهر | غير مذكور في صفحة الحدود (غير مؤكد) | يُحسب من 300 رصيد/شهر (20 رصيد لكل GB) |
| البناء | حد مرن 10 بناء/ساعة، مهلة 10 دقائق | 500 بناء/شهر، بناء واحد متزامن | النشر 15 رصيد لكل نشر إنتاجي |
| دومين خاص | مدعوم | 100 دومين لكل مشروع | مدعوم |
| عند التجاوز | — | — | الخطة المجانية حد صارم: نفاد الرصيد يوقف الموقع كله («Site not available») حتى الشهر التالي أو الترقية |
| الاستخدام التجاري | سياسة GitHub تمنع استخدامه كاستضافة تجارية/SaaS: **يحتاج رأي loyer** | مسموح (غير مؤكد نص صريح) | مسموح (غير مؤكد نص صريح) |
| `_redirects` | لا | نعم | نعم |
| المصدر | [GitHub](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits) | [Cloudflare](https://developers.cloudflare.com/pages/platform/limits/) | [Netlify pricing](https://www.netlify.com/pricing/) |
أحجامنا (صفحات HTML صغيرة) بعيدة جداً عن الحدود، لكن توقف Netlify الكامل عند نفاد الرصيد خطر على شرائح مطبوعة.

**التوصية:** Cloudflare Pages أساسي، Netlify احتياط. GitHub Pages مشال من الاحتياط حتى يعطي loyer رأيه. القرار والتسجيل لصاحب المشروع.

## 6. قواعد السجل
- الكود: حروف إنجليزية صغيرة وأرقام 3-16، فريد، ما يتكرر أبداً ولو بعد إلغاء.
- **لا يُحذف رابط منشور أبداً**: الإلغاء = `"status": "cancelled"` فيتحول إلى `/t/inactive/`. الحذف يخلي الشريحة المطبوعة تفتح 404.
- إعادة استخدام شريحة لعميل جديد = تغيير `dest` و`client` مع ملاحظة التاريخ (سجل git يحفظ التاريخ).
- قبل البرمجة: `node systems/shortlinks/build.js` ثم خذ الرابط من `links.txt`.
- مطبّق في البناء (جولة 3): أكواد محجوزة (مثل `inactive`) ممنوعة، فحص الوجهة (https ورابط صالح)، منع حذف أي كود منشور عبر مقارنة `links.json` بـ `published.txt` (البناء يفشل لو كود منشور اختفى)، وتمرير `?src=` فقط (nfc/qr) للوجهة، وأي باراميتر ثاني ينشال.

## 7. الإحصائيات (عدد اللمسات بدون بيانات شخصية)
الاستضافة الثابتة ما تعد الزيارات لكل رابط بشكل موثوق من ملفاتنا. الخيارات (تصميم، لم يُبنَ):
- Cloudflare Web Analytics (بدون كوكيز حسب وصف Cloudflare؛ التفاصيل غير مؤكدة) مع سكربت في صفحة التحويل. ملاحظة: التحويل 302 من `_redirects` لا يحمّل الصفحة فلا يُعد؛ للعد نحتاج مرور الزائر بصفحة HTML (ثانية تأخير تقريباً) أو عداد بسيط لاحقاً على Cloudflare Workers (غير مؤكد الحدود المجانية).
- القاعدة: نعد (الكود، التاريخ، الساعة) فقط. لا IP ولا جهاز ولا موقع ولا كوكيز.
- إضافة `?src=nfc` و`?src=qr` للتفريق بين الشريحة والباركود (اختياري).

## 8. تصميم إشعار «تشيك أوت» لباقة المضيف (ورق فقط، لم يُبنَ)
مبني على شروط GM-003 في `work/2026-09-27-service-ideas/decision.md`.

**المسار:** الضيف يلمس شريحة الوحدة → `/t/<code>` → صفحة «دليل الوحدة» فيها زر «تم الخروج». الضيف لا يدخل أي بيانات.
1. الضغط على الزر يرسل طلباً لنظامنا (نقطة خلفية صغيرة، مثلاً Worker أو n8n، تحتاج قرار) فيه كود الوحدة فقط. كود الوحدة **عشوائي 12 حرفاً أو أكثر** (مو `unit01`) عشان ما أحد يخمنه ويرسل إشعارات كاذبة.
2. نظامنا يرسل الإشعار **من رقمنا** للمضيف والعاملة. أرقامهم مخزنة عندنا فقط ولا تظهر في الصفحة أو الرابط أو الكود المصدري أبداً.
3. نص الإشعار: «الوحدة <اسم> — الضيف ضغط تم الخروج الساعة <وقت>. **تأكد قبل الدخول**.»

**حد الإرسال (حماية من اللمسة الكاذبة):** زر تأكيد ثاني («متأكد؟») قبل الإرسال. الحد ما يحجب إشعاراً حقيقياً: الضغطة الأولى ترسل عادي، وأي ضغطة ثانية خلال 6 ساعات (رقم مبدئي يحدده المضيف) **ترسل أيضاً لكن بعلامة «ضغطة مكررة»**، وبعدها سقف (مثلاً 3 في الساعة) يمنع الإغراق.

**بيانات الضيف:** نظامنا لا يسجل شيئاً عنه: لا اسم ولا رقم ولا كوكيز. السجل = (كود الوحدة، الوقت) فقط. سجل الـ IP عند مزود الاستضافة/الخادم نفسه: غير مؤكد (يُراجع في إعدادات المزود قبل البناء).

**رقم العاملة:** يُسجل فقط بعد موافقتها الموثقة (تاريخ ووسيلة الموافقة). عند إلغاء الخدمة أو انتهاء عملها أو طلبها: **يُحذف فوراً** من كل أنظمتنا، والمدة النظامية (عند loyer) حد أعلى فقط لما يتأخر خارج يدنا (نسخ احتياطية عند المزود). يُسجل تاريخ الحذف بدون الرقم.

**شروط البيع:** مضيف مرخص من وزارة السياحة فقط، والصفحة ما فيها أي رابط حجز أو دفع خارج المنصة.

**غير مؤكد قبل البناء:** قناة الإرسال (WhatsApp Business API: الاشتراطات والتكلفة غير مؤكدة؛ البديل SMS أو بريد أو تيليجرام)، نص نظام حماية البيانات من سدايا (عند loyer)، ومكان تخزين الأرقام.
