# Smart Stay — تصميم النظام (sys-architect، 2026-10-01)

**ترتيب الشغل (طلب صاحب المشروع):** «بعد ما تدرسه صمم الموقع قبل الشبكة».
يعني صفحات الضيف والمضيف (افتح الباب، الحجوزات) تتصمم وتتعتمد أول، والشبكة (n8n والقفل) تُبنى بعدها على نفس الشاشات.
هذا الملف يحدد **وش تحتاج الصفحات من الشبكة** (حقول، حالات، رسائل خطأ)، عشان مصمم الموقع يبدأ منه. ولاحظ إن قسم الموقع موقوف (GM-065)، وما يرجع إلا بطلب من صاحب المشروع.
وضع التجهيز (GM-006): كل شي هنا تصميم وملفات بس. ما فيه نشر، ولا حسابات، ولا شراء أقفال، ولا workflow منشور.

## 1. الصفحات أولاً (مدخل لمصمم الموقع)

**الخلاصة:** iCal يعطينا التواريخ بس، وكثافة التحديث غير مؤكدة (تقريباً كل ساعات، مو لحظي). عشان كذا **الرابط للضيف ينولد ويرسله المضيف بنفسه** داخل رسالة المنصة. ما نحتاج رقم الضيف أبداً، وهذا أحسن للخصوصية.

## 3. المعمارية
```
NFC/QR على الباب → /t/<code>/ (ثابت، systems/shortlinks) → /door/?u=<unit>
الضيف يفتح الرابط اللي أرسله المضيف: /door/?u=<unit>#k=<token>
صفحة door (static) ── POST {unit, token} ──► n8n Webhook "LT door open"
   n8n: تحقق التوكن → تحقق الوقت → حد المحاولات → Lock Cloud API → سجل → تنبيه تليجرام
```
- **التوكن:** 128 bit عشوائي (base64url، 22 حرف). يتخزن في n8n Data Table **كـ hash بس (SHA-256)**، ويرتبط بـ `booking_id, unit, valid_from, valid_to`.
- **مدة الصلاحية:** من وقت الدخول ناقص ساعة، لين وقت الخروج زائد 30 دقيقة. الأرقام مقترحة، والمضيف يقدر يغيرها.
- **التوكن بعد `#`:** ما يروح للسيرفر في طلب الصفحة، فما ينحفظ في سجلات الاستضافة. هذي خاصية في المتصفحات (RFC 3986 §3.5).
- **الشريحة ما فيها سر.** الشريحة على الباب علنية. هي تفتح الصفحة بس، والصفحة تاخذ التوكن من الرابط اللي وصل الضيف، أو من `localStorage` لو الضيف فتحه قبل كذا على نفس الجوال.
- **القفل:** نتعامل معه من خلال طبقة `lock_adapter` في n8n، وما نربط النظام بقفل واحد:
| القفل | API سحابي | فتح عن بعد | PIN مؤقت | يحتاج Gateway | المصدر |
|---|---|---|---|---|---|
| TTLock (ماركات كثيرة) | Open Platform | نعم | نعم (PIN بفترة) | غالباً نعم (G2/G3) | https://open.ttlock.com/doc — غير مؤكد |
| Nuki | Web API | نعم | نعم (keypad) | Bridge أو Smart Lock 4 Wi-Fi | https://developer.nuki.io — غير مؤكد |
| Tuya / Smart Life | Cloud API | يعتمد على الموديل | يعتمد على الموديل | يعتمد على الموديل | https://developer.tuya.com — غير مؤكد |
اختيار القفل وتوفره في جدة وسعره: شغل **مهندس NFC**. أقترح TTLock لأن ماركات كثيرة تستخدمه (غير مؤكد).

## 4. مخطط الـ n8n (node-level، بدون credentials)
**W1 `LT door open`** (Webhook POST)
1. Webhook `/door-open` (CORS لدوميننا بس) ← 2. Code: تحقق الشكل (`unit` بنفس قاعدة `^[a-z0-9]{3,16}$`، والتوكن 22 حرف) ← 3. Data Table `rate_limit`: لو فيه أكثر من 5 محاولات غلط من نفس `unit` خلال 15 دقيقة، أو أكثر من 3 فتحات ناجحة في الدقيقة، يرد 429 ← 4. Crypto SHA-256 ← 5. Data Table `bookings` get by hash+unit ← 6. IF موجود وحالته `active` والوقت الحين داخل الفترة ← 7. HTTP Request `lock_adapter.unlock(lock_id)` (timeout 10s، retry 1) ← 8. Data Table `audit_log` insert ← 9. Telegram: «انفتح باب <unit> — حجز <ref> — <الوقت>» للمضيف ولنا (GM-048) ← 10. Respond `{status}`.
   - **فشل القفل أو timeout:** يرد `{status:"offline", pin}` ويعرض PIN الحجز، وينبهنا على تليجرام فوراً.
   - **أي رفض:** نفس الرد العام `denied`، عشان ما نكشف السبب.

**W2 `LT ical sync`** (Schedule كل 30 دقيقة)
HTTP GET لكل رابط iCal ← Code: يحلل VEVENT (DTSTART/DTEND/UID) ← Upsert في `bookings` بمفتاح UID ← لو فيه حجز جديد: تليجرام للمضيف فيه زر «ولّد رابط الضيف». لو حجز انلغى: `status=cancelled`، والتوكن ينلغي، والـ PIN ينحذف.

**W3 `LT booking token`** (زر تليجرام أو Webhook من اللوحة)
يولد توكن وPIN (6 أرقام) ← يحفظ الـ hash ← ينشئ PIN مؤقت في القفل للفترة نفسها ← يرسل للمضيف رسالة جاهزة ينسخها للضيف فيها الرابط والـ PIN. **نحن ما نرسل للضيف** (ما عندنا رقمه).

**W4 `LT stay events`** (Schedule كل 15 دقيقة)
- قبل الدخول بـ 24 ساعة: تذكير للمضيف لو ما انرسل رابط للضيف.
- وقت الخروج زائد 30 دقيقة: التوكن ينتهي، والـ PIN ينحذف من القفل.
- يطلع حدث `checkout` لو الضيف ما ضغط «تم الخروج». يدخل نفس مسار التشيك أوت (GM-048)، ويطلع معه زر «أرسل للنظافة» (GM-067). رمز النظافة **منفصل** عن رمز الضيف (`services/cleaning.md`).

**الجداول (n8n Data Tables):** `units(unit, host_chat, lock_id, ical_urls)`, `bookings(uid, unit, ref, from, to, token_hash, status)`, `audit_log(ts, unit, ref, action, result)`, `rate_limit`.
`lock_id` والتوكنات الخام وكلمات المرور ما تنكتب في أي ملف في المستودع. صاحب المشروع يحطها بنفسه في credentials حق n8n.

## 5. نموذج التهديدات
| التهديد | الحماية |
|---|---|
| الضيف يشارك الرابط | التوكن مربوط بفترة الحجز بس، وكل فتح ينسجل ويوصل تنبيه للمضيف، والمضيف يقدر يلغي التوكن بزر واحد. ونكتبها في الشروط: «الرابط لضيوف الحجز» |
| إعادة إرسال الطلب (replay) | ما ينفع برا فترة الحجز. وداخلها نفس صلاحية الضيف، فما يضيف خطر. HTTPS إجباري |
| تخمين التوكن (brute force) | 128 bit + حد 5 محاولات غلط لكل وحدة كل 15 دقيقة + تنبيه لنا لو تجاوزها |
| الجوال ضاع | المضيف يضغط «إلغاء»، وW3 يولد توكن جديد وPIN جديد |
| القفل فاصل أو النت طايح | PIN الكيباد يشتغل بدون نت (يعتمد على القفل، غير مؤكد) + المفتاح الميكانيكي عند المضيف. **ما نبيع خدمة الفتح لقفل ما فيه كيباد** |
| n8n طايح | نفس الحل: PIN. ونراقب W1 بـ Error Workflow يرسل تنبيه تليجرام |
| الشريحة تنبدّل | الشريحة تفتح صفحة بس، وما فيها سر. القفل حسب `architecture.md` الحالي (مهندس NFC) |

## 6. الاحتفاظ بالبيانات
- ما نخزن اسم الضيف ولا رقمه أبداً. نخزن `ref` المنصة بس، لو المضيف دخله.
- `bookings`: تنحذف بعد الخروج بـ 30 يوم. `audit_log`: 180 يوم (مقترح، يحسمه **loyer** حسب نظام حماية البيانات الشخصية PDPL — غير مؤكد).
- الـ hash ينحذف وقت ما ينتهي الحجز.

## 8. MVP مقابل v2
**MVP:** إدخال الحجز من تليجرام (يدوي) + W1 + W3 + W4 + صفحة door + قفل واحد (TTLock، بعد ما يأكده مهندس NFC) + PIN احتياطي + سجل وتنبيهات.
**v2:** مزامنة iCal (W2) + لوحة `/host/` + أكثر من نوع قفل + تقرير شهري للمضيف + جاذر إن (لو ثبت إن عنده iCal).

## 9. التكلفة التشغيلية (تقدير، غير مؤكد)
- n8n: نفس الاشتراك الحالي. كل فتح يصرف تقريباً execution واحد. عدد الـ executions المسموح في خطتنا غير مؤكد. W2 وW4 يصرفون تقريباً 4,300 تنفيذ بالشهر (2,880 + 1,440)، **حتى لو ما فيه ولا حجز**. ممكن نخفف الوتيرة.
- API القفل: TTLock Open Platform مجاني حسب ما ينذكر عادة (غير مؤكد). سعر القفل والـ Gateway يحددهم مهندس NFC والمالي.

## 10. أسئلة مفتوحة
1. هل جاذر إن يصدّر iCal؟ (صاحب المشروع يسأل الدعم، أو مضيف عنده حساب)
2. أي قفل نعتمد، وهل متوفر في جدة مع Gateway؟ (مهندس NFC)
3. هل نرجّع قسم الموقع (GM-065) عشان يصمم صفحة door أول، مثل ما طلب صاحب المشروع؟
4. مدة احتفاظ السجلات، وبند مشاركة الرابط في الشروط. (loyer)
5. حد الـ executions في خطة n8n الحالية.
